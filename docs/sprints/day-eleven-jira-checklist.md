## Authentication and guest-use direction

The product must support username/password, verified phone-number sign-in and Google/Gmail sign-in, with more methods added later. Each method is optional for an individual user; an account needs at least one verified sign-in method, but username/password need not be mandatory. Google sign-in means redirecting through Google's OpenID Connect flow, never asking for or storing a Google password. Phone sign-in uses a one-time verification code and will need a provider, abuse controls and an explicit cost check. Linking a new method must prove control of that method and an existing account; a matching email or phone alone must not silently merge accounts.

Guest mode must work without a server account. Guest-created notes stay in volatile client memory and are not sent to or stored by Merlin's server. Tell the user they may lose them when the session ends. After login, offer an explicit review/import action; save imported notes only under the actor derived from the verified credential. Do not accept a client-selected owner ID. This multi-method, multi-device and guest-import direction is product scope, not built behavior or a Day 11 commitment.

Day 11's candidate route slice is a pre-created synthetic username/password account with `POST /auth/login` and `GET /me`. Authorized assistant work adds FastAPI/Uvicorn dependencies, password/token/Redis primitives, credential/refresh schema, runtime bootstrap and focused tests. `app.health_server` now delegates its normal module command to `app.runtime.main`, which validates environment configuration, checks the least-privilege PostgreSQL login, injects storage/limiter/keys and starts the composed ASGI app on loopback with proxy-header rewriting disabled. The direct `app.api_server.run_api_server` entry point remains available for callers that inject dependencies themselves. `/me` validates the fixed EdDSA token and returns only its subject. Phone/Google sign-in, account linking, guest import and authenticated notes routes remain deferred. Docker Compose already provides a digest-pinned Redis service bound to loopback with persistence disabled; reuse it rather than adding a duplicate. That local service is not a production Redis security configuration.

### 2. Specify the authentication boundary — 60 minutes

- [x] In your own words, explain how a password becomes a one-way hash, how a signed short-lived token is validated, and how the server derives the actor from that validated token. Decide the minimum login and current-user behavior, token lifetime, error response, and required negative cases. Do not use a request-supplied `user_id` as identity. **Learner explain-back and decisions, reviewed October 24:** use Argon2id password hashing; EdDSA/Ed25519 signed access tokens; `Authorization: Bearer`; 10–15-minute access token plus rotating refresh token; `POST /auth/login`; and `GET /me`. Use one error shape, `{ "error": "<code>", "message": "<text>" }`, prevent username enumeration, and prioritize rate limiting. Refresh policy: opaque tokens, PostgreSQL stores only token hashes, per-device family, 30-day idle and 90-day absolute expiry, rotation, reuse detection and family revocation. Rate limits: 5 failed logins per normalized username and 20 per client IP per 15 minutes, with `429` and `Retry-After`. Libraries: `argon2-cffi`, `PyJWT` + `cryptography`, and `redis-py`, with exact versions and hashes pinned in the lockfile after compatibility review. Password hashing is one-way hashing with a unique salt and work factor, not encryption; stolen hashes can still be attacked with guesses. Validate signature using a fixed algorithm and check expiry and expected issuer/audience. A JWT is signed, not necessarily encrypted. Derive actor from verified token subject, not request `user_id` or password. These are design decisions, not implemented auth.

**Minimum request/response table:**

| Request | Success | Denial |
|---|---|---|
| `POST /auth/login` with username/password | `200`, a short-lived bearer access token and its expiry | Unknown username and wrong password share `401`, error code and message; rate limit returns `429` without revealing account existence |
| `GET /me` with `Authorization: Bearer <access_token>` | `200`, the account identity selected from the verified token subject | Missing, malformed, modified, expired, wrong-algorithm, wrong-issuer or wrong-audience token fails closed with the common authentication error shape |

Use the consistent body `{ "error": "<code>", "message": "<text>" }`. Never log passwords, raw access/refresh tokens or private account data. Refresh lifecycle is specified; its HTTP endpoints remain outside the first login/current-user route slice.

**Required negative cases:** wrong password; unknown username with an indistinguishable response; missing/empty/malformed credentials; invalid or disabled account if supported; absent bearer token; malformed, tampered, expired, wrong-algorithm, wrong-issuer and wrong-audience access token; attempted identity override via request `user_id`; both rate limits, window reset, `Retry-After`, concurrent attempts and Redis failure; and safe error/log output. Before implementing persistent refresh sessions, test expiry, rotation, replay detection with family revocation, logout and per-device isolation. Phone OTP abuse/replay/expiry, Google OIDC state/nonce/issuer/audience/callback validation, safe account linking, and explicit guest-note import are separate future gates.

**Credential operations:** access token lifetime is 10–15 minutes (use 15 minutes for the first slice). Refresh tokens are opaque, cryptographically random values; store only token hashes in PostgreSQL, with one token family per device, 30-day idle expiry and 90-day absolute maximum. Rotate after each successful refresh in one atomic transaction. Retain hashes of consumed tokens until family expiry so reuse is detectable; reuse revokes that whole family. Tests must cover expiry, rotation, concurrent refresh, replay detection, family revocation, logout and isolation between devices. Web clients need secure, HttpOnly, SameSite cookie handling and CSRF/origin protection; native clients need platform secure storage. Migration 003 now supplies credential/session storage and database expiry/consumption guards; request handlers and the atomic refresh/reuse service are still absent.

Rate-limit failed logins in Redis: at most 5 failures per normalized username and 20 failures per client IP during a rolling 15-minute window. Return `429` with `Retry-After`; use the same response shape and behavior for existing and nonexistent usernames. Derive client IP only from the socket peer or a configured trusted proxy. Use a keyed HMAC of the normalized username for Redis keys, with a separate random secret shared by app instances; never put raw usernames in keys or logs. Make sliding-window updates atomic (for example, a Redis script), expire all limiter keys, and fail closed with a safe `503` if Redis is unavailable. Avoid permanent account lockout: it lets attackers deny service to a known username. Test both thresholds, rolling-window expiry, `Retry-After`, concurrent attempts, username normalization, proxy trust, Redis failure and non-disclosure.

**Rate-limit trade-off to review before public rollout:** an attacker can spend five attempts on a target username and temporarily trigger the 15-minute username limit for that person, even from another IP. The 20-per-IP cap can also affect people sharing a home, school or mobile-network address. Keep the selected values for the learning design, but evaluate a step-up challenge or progressive delay before exposing login broadly.

Use `argon2-cffi` for Argon2id, `PyJWT` with `cryptography` for EdDSA/Ed25519, FastAPI/Uvicorn for the later HTTP slice, and `redis-py` for Redis. Exact versions and package hashes are now pinned in `pyproject.toml` and `uv.lock`. PyJWT's official usage guide says EdDSA requires `cryptography` ([PyJWT documentation](https://pyjwt.readthedocs.io/en/latest/usage.html)); Redis documents rate-limit implementations using atomic operations and scripts ([Redis rate limiter guide](https://redis.io/docs/latest/develop/use-cases/rate-limiter/)).

Do not claim refresh endpoints, live rate limiting on login or multi-device session security as finished: routes and their database transactions are not connected. The local Redis server already exists in Compose; reuse it.

**Signing-key cost check (October 24, 2026):** a local Ed25519 development key can be generated without a cloud bill, but must stay out of source control and is not a managed KMS/HSM. AWS KMS supports Ed25519 signing, but a customer-managed key costs $1/month and asymmetric API requests are excluded from the free request tier ([AWS KMS algorithms](https://docs.aws.amazon.com/kms/latest/developerguide/symmetric-asymmetric.html), [AWS KMS pricing](https://aws.amazon.com/kms/pricing/)). Google Cloud KMS supports Ed25519; manually created software keys have a small recurring key-version and operation charge. Its free Autokey tier is limited to Autokey-created keys, whose documented default purpose/algorithm is AES-256-GCM for integrated resources, so it is not established as a free JWT-signing key ([Google KMS algorithms](https://docs.cloud.google.com/kms/docs/algorithms), [pricing](https://cloud.google.com/kms/pricing), [Autokey overview](https://cloud.google.com/kms/docs/autokey-overview)). Azure Key Vault's documented signing algorithms do not include EdDSA, so it does not match this selected algorithm ([supported key algorithms](https://learn.microsoft.com/en-us/azure/key-vault/keys/about-keys-details)). No always-free managed Ed25519 KMS/HSM option was verified. Token signatures can be checked locally with a cached public key; call KMS only when minting or refreshing tokens. For local work use a development-only software key; production KMS requires an explicit cost/provider decision.
